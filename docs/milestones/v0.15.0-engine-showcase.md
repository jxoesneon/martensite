# Milestone Specification: v0.15.0 — Engine Showcase

## 1. Executive Summary & Objectives

Milestone `v0.15.0` builds the two flagship integrations on the
v0.14.0 external-surface foundation: a **Bevy 3D viewport** embedded in
Martensite (host mode: Martensite owns the window, wgpu device, and
compositing; Bevy renders headless into a Martensite-owned texture) and a
**Godot 4 GDExtension** that produces frames Martensite displays.

The headline targets are:

- **Bevy viewport at full frame rate with zero GPU copy** — Bevy's final
  tonemapped output is written directly into a Martensite-created
  `wgpu::Texture` via `RenderTarget::TextureView`, then composited by
  the v0.14.0 pipeline. Same `wgpu::Device`/`Queue` shared through
  `RenderCreation::Manual`.
- **Godot viewport functional and honest about its cost** — research
  established that true zero-copy from Godot is **impossible without
  engine patches** (§4.3). v0.15.0 ships the reliable path
  (`texture_get_data_async` readback → `queue.write_texture`) and gates
  the one-GPU-copy experimental path behind a feature flag, with the
  engine-patch requirements documented.

- **Example app**: `examples/viewport_showcase` — Bevy 3D scene and

  shell chrome.

## 4. Architectural Deliverables & Implementation Specifications

### 4.1. Bevy Host-Mode Embed (`martensite-bevy`)

**Device sharing — the only clean path.** `wgpu::Texture` objects are
device-bound; wgpu exposes no device-exportable handles. Martensite
creates the `Instance`/`Adapter`/`Device`/`Queue` and injects them:

```rust
RenderPlugin {
    render_creation: RenderCreation::Manual(RenderResources(
        RenderDevice::from(wgpu_device),
        RenderQueue(Arc::new(WgpuWrapper::new(wgpu_queue))),
        RenderAdapterInfo(WgpuWrapper::new(adapter.get_info())),
        RenderAdapter(Arc::new(WgpuWrapper::new(adapter))),
        RenderInstance(Arc::new(WgpuWrapper::new(instance))),
    )),
    synchronous_pipeline_compilation: true,
    ..default()
}
```

**Viewport target:** each `ExternalEngine` viewport owns a
Martensite-created `wgpu::Texture` (`TEXTURE_BINDING |
RENDER_ATTACHMENT`, `Bgra8UnormSrgb` default). Its `TextureView` converts
via `impl From<wgpu::TextureView> for bevy TextureView` and registers in
`ManualTextureViews`; the `Camera3d` uses
`RenderTarget::TextureView(handle)`. Bevy's post-processing chain
(tonemapping, bloom) resolves into `ViewTarget::out_texture` — the
host-owned texture — so no readback step exists.

**Frame pump:** per Martensite frame —
`sub_apps.update()` → `RenderDevice::poll(PollType::Wait)` →
`notify_frame_ready`. `PipelinedRenderingPlugin` is omitted in v0.15.0
(would need a GPU fence before sampling).

**wgpu version constraint (hard dependency finding):** released Bevy
0.19.x uses `wgpu ^29`; wgpu 30 landed only on `main` for the 0.20
milestone (bevyengine/bevy#24841). Options, decided at implementation:

1. Pin `bevy = { git = ".../bevy", rev = "<main-sha>" }` — accepted for
   the example/adapter; documented as pre-release coupling.
2. Vendor a minimal 0.19 fork with the wgpu-30 backport.
3. If Bevy 0.20 releases during implementation, use it.

The adapter is an optional workspace member; a `bevy` version bump is a
`martensite-bevy` concern and must not destabilize core crates.

### 4.2. Input Forwarding

`MartensiteInputPlugin` (Bevy `PreUpdate`):

- Clear and re-press `ButtonInput<KeyCode>`/`ButtonInput<MouseButton>`
  via `bypass_change_detection` from host events.
- Send `PointerInput` events carrying `Location { target:
  NormalizedRenderTarget::TextureView(handle), position }` so
  `bevy_picking` raycasts hit-test inside the viewport.
- Scroll → `MouseWheel` events; IME text → `KeyboardInput` events.

### 4.3. Godot GDExtension (`martensite-godot`)

**What research established (must be stated in docs honestly):**

- `RenderingDevice::texture_get_native_handle` /
  `get_driver_resource(DRIVER_RESOURCE_TEXTURE)` return API object
  pointers (`VkImage`, `ID3D12Resource*`, `id<MTLTexture>`) — **not**
  cross-process/shareable handles.
- Godot's internal render targets are **not** allocated with
  `D3D12_HEAP_FLAG_SHARED` / `VkExportMemoryAllocateInfo` / IOSurface
  backing — a GDExtension cannot retroactively add export flags.
- `fence_create`/`semaphore_create`/cross-API sync are **not** exposed
  to GDExtension; the only public completion primitive is the CPU-side
  `texture_get_data_async` callback.
- `libgodot` (merged to Godot master) puts Godot in-process but does
  **not** solve logical-device sharing.

**Therefore the milestone ships two tiers:**

**Tier 1 — Readback path (required, shippable):**
`SubViewport` → `ViewportTexture` → `texture_get_rd_texture` →
`RenderingDevice::texture_get_data_async` → `PackedByteArray` → channel
→ `queue.write_texture` into the viewport texture. Works on every Godot
driver (Vulkan/D3D12/Metal/GL) and every platform. Not zero-copy;
throughput and latency are measured and published, not hidden.

**Tier 2 — Shared-texture blit (feature-gated `godot-gpu-copy`,
experimental):** Martensite allocates a shareable wgpu texture
(`HEAP_FLAG_SHARED` / exportable Vulkan memory / IOSurface-backed Metal),
imports it into Godot via `texture_create_from_extension`, and a
`CompositorEffect` at `EFFECT_CALLBACK_TYPE_POST_TRANSPARENT`
`texture_copy`s the `RenderSceneBuffersRD` color buffer into it. One GPU
copy — still not zero-copy, and requires per-platform unsafe code in the
extension crate. Synchronization is best-effort (one-frame delay
tolerance) until Godot exposes fence APIs.

**Explicitly out of scope:** patching Godot itself. The spec documents
the four engine changes that would unlock true zero-copy (export-flagged
internal targets, external-texture render targets, public fence/semaphore
API, merged `libgodot_set_native_window`) as upstream-contribution
opportunities.

### 4.4. Example & Verification Application

`examples/viewport_showcase`: a Martensite window with native chrome
(v0.13.0 shell) containing (a) a Bevy PBR scene in an `ExternalEngine`
widget, (b) the Godot viewport, (c) ordinary Martensite widgets around
them — proving UI compositing over live engine content.

|------|-----------|--------------|
| Bevy zero-copy | Bevy viewport composites with zero `write_texture`/readback; `RenderTarget::TextureView` confirmed as destination | Integration test + instrumentation counter |
| Bevy frame rate | Rotating-scene viewport sustains 120fps on reference GPU | `#[ignore]`-gated perf test on GPU runner |
| Bevy input | Pointer events pick objects in the embedded scene | Headless test via `bevy_picking` hit result |
| Bevy resize | Viewport resize renegotiates texture without panic/leak | Unit test |
| Godot readback | Frames flow SubViewport→Martensite widget; measured throughput + latency published | Integration test (mocked at CI; real Godot run `#[ignore]`) |
| Godot honesty | Docs state copy count and engine-patch requirements; no "zero-copy" claim for Godot | Doc review |
| All gates | fmt, clippy (default + all-features), tests, doctests, docs, audit, deny, vet | Full CI suite |

  optional workspace member.

  build.

## 7. Unsafe Code Policy

- `martensite-bevy`: `#![forbid(unsafe_code)]` — the `RenderCreation::
  Manual` injection path is safe Bevy/wgpu API.
- `martensite-godot`: FFI boundary by nature (GDExtension). Unsafe
  confined to the extension crate; the Tier-2 shared-handle path
  (`create_texture_from_hal`-adjacent) documents every `unsafe` block.
  `AGENTS.md` allowed-unsafe list gains `martensite-godot`.
