# Milestone Specification: v0.12.0 — Blessed Widgets & Kinematics

## 1. Executive Summary & Objectives

Milestone `v0.12.0` delivers production-grade virtualized data grids, a
binary-space-partitioning docking shell, iOS-style rubber-band scroll
kinematics, and 6-DoF Kalman-filtered stylus input. These four subsystems
close the gap between Martensite's core rendering/text engine and the
interactive surface that industrial users expect from a modern retained-mode
GUI framework.

The headline performance targets are:

- **1,000,000-row virtualized DataGrid** scrolling at a steady **120 fps**
  with zero per-frame heap allocation.
- **BSP docking tree** with multi-swapchain panel rendering and **zero
  allocation during split/merge** operations.
- **0.55 rubber-band** overscroll physics matching iOS scroll-view behavior.
- **6-DoF Kalman stylus** input pipeline with end-to-end **latency < 2.0 ms**.

---

  - `data_table`: Enhanced virtualized DataGrid with column sorting,

## 4. Architectural Deliverables & Implementation Specifications

### 4.1. 1,000,000-Row Virtualized DataGrid

The existing `DataTable<T>` provides basic virtualized row iteration. The
v0.12.0 enhancement brings it to production quality:

- **Zero-allocation scroll path**: `visible_rows()` returns an iterator
  that borrows directly from the row storage. No `Vec`, no `Box`, no
  intermediate collections. The scroll offset update (`set_scroll_offset`)
  is a single `f64` assignment. Column header geometry is precomputed at
  configuration time, not per-frame.

- **Column sorting**: `ColumnSort` (ascending/descending/none) per column.
  Sorting uses `sort_unstable_by` on an index vector (`Vec<usize>`) that
  is built once when sort changes and reused during scroll. The index is
  `Vec`-backed but allocated only on sort change, not per scroll frame.

- **Filtering**: `RowFilter` predicate applied to the index vector. Filtered
  index is rebuilt only when the filter or data changes, not per frame.

- **Range selection**: `SelectionModel` tracking contiguous and
  discontiguous row ranges. Selection state is `SmallVec`-backed (inline
  for small selections, heap-allocated only when the selection grows
  beyond the inline capacity).

- **Keyboard navigation**: Arrow keys, PageUp/PageDown, Home/End,
  Ctrl+Home/Ctrl+End, Shift+arrow for range selection. The key handler
  updates the focused row index and auto-scrolls to keep it visible.

- **Column resize and reorder**: `ColumnConfig` with width, visibility,
  and order. Resize updates a single `f64`; reorder swaps two indices in
  the column order vector.

- **Accessibility**: Each visible row exposes an AccessKit node with
  `Role::Row`, `Role::Cell` children, and `Action::Click` /
  `Action::Focus` actions. Column headers expose `Role::ColumnHeader` with
  sort state.

- **Performance gate**: 1M-row `visible_rows()` iteration completes in
  < 8.3 ms (120 fps budget) on CI reference runners. The existing timing
  gate in `tests/plugins_blessed_integration.rs` is retained and extended
  with a steady-state scroll simulation (1000 consecutive scroll offsets,
  measuring per-frame allocation count via a custom allocator hook).

### 4.2. BSP Docking Tree

A binary space partitioning tree manages dockable panel layouts:

- **Data structure**: `DockTree` is a recursive binary tree where each
  internal node is a `DockSplit` (horizontal or vertical) with a split
  ratio `f64 ∈ (0.0, 1.0)`, and each leaf is a `DockPanel` containing a
  widget ID and an optional swapchain surface handle.

- **Zero-allocation split**: `DockTree::split_leaf(node_id, direction,
  ratio)` transforms a leaf into an internal node with two leaf children.
  The tree uses a `Slab<DockNode>` arena with pre-allocated capacity.
  Splits within the capacity budget do not allocate. The arena grows
  amortized (doubling) only when capacity is exceeded, which is a
  configuration event, not a per-frame operation.

- **Zero-allocation merge**: `DockTree::merge(node_id)` collapses an
  internal node back into a leaf. The children are marked as free slots
  in the slab and reused by the next split. No deallocation or allocation.

- **Multi-swapchain**: Each `DockPanel` can optionally own a
  `wgpu::Surface` handle. When a panel is resized (split ratio change),
  only the affected surface is reconfigured. The `DockSurfaceManager`
  tracks dirty panels and reconfigures only those surfaces in the next
  render pass.

- **Drag-and-drop docking**: `DockDragSession` tracks a floating panel
  being dragged over the dock tree. Hit-testing against dock zones
  (center, left, right, top, bottom, tab) produces a `DockDropTarget`
  that previews the resulting split. On drop, the tree is restructured
  with a single `split_leaf` or `merge` call.

- **Serialization**: `DockTree::to_layout()` / `DockTree::from_layout()`
  for persistence. Layout is a flat `Vec<DockNodeLayout>` that can be
  serialized to any format.

- **Performance gate**: `split_leaf` and `merge` complete in < 1 µs with
  zero heap allocations when within slab capacity. Verified by a
  `#[ignore]`-gated benchmark that performs 10,000 split/merge cycles and
  asserts zero allocation via a counting allocator.

### 4.3. 0.55 Rubber-Band Overscroll

iOS-style rubber-band scrolling physics:

- **Stretch coefficient**: `RUBBER_BAND_COEFFICIENT = 0.55`. When the
  scroll offset exceeds the content bounds, the visible offset is:
  `visible_offset = boundary + (delta * 0.55)` where `delta` is the
  overscroll distance. This produces the characteristic diminishing
  stretch where each additional pixel of drag moves the content less.

- **Directional axis lock**: Once a drag gesture establishes a primary
  axis (horizontal or vertical), the rubber-band effect is applied only
  on that axis. Cross-axis drift is suppressed.

- **Spring-back release**: When the drag is released, the overscroll
  decays back to the boundary using the existing `SpringSolver` from
  `martensite-motion`. The spring config uses a critically-damped
  profile (ζ = 1.0) with a stiffness tuned for ~300 ms settle time.

- **Velocity handoff**: If the user releases with velocity (fling), the
  rubber-band transitions to the spring-back phase with the fling
  velocity as the initial condition. The spring absorbs the velocity
  and settles at the boundary.

- **Integration**: `RubberBandScroller` is a standalone struct that wraps
  a content offset and content size. It does not depend on any widget
  system — it is pure physics. Widgets call `RubberBandScroller::drag`,
  `RubberBandScroller::release`, and `RubberBandScroller::visible_offset`
  per frame.

- **Performance gate**: `RubberBandScroller::visible_offset` is `O(1)`
  with zero allocation. The spring-back update is `O(1)` per frame.

### 4.4. 6-DoF Kalman Stylus Input

A Kalman filter for stylus/pen input smoothing with 6 degrees of freedom:

- **State vector**: 12-dimensional Kalman state:
  - Position: `x, y, z` (3)
  - Velocity: `vx, vy, vz` (3)
  - Orientation: `tilt, twist, azimuth` (3)
  - Angular velocity: `ω_tilt, ω_twist, ω_azimuth` (3)
  - Pressure is filtered separately with a 1-D Kalman (2-state: value +
    rate of change).

- **Measurement model**: Each stylus event from `winit::event::Tablet`
  provides `x, y, pressure, tilt, twist` (azimuth is derived from
  `tan2(y, x)` when the tablet reports tilt direction). The measurement
  matrix `H` maps the 12-state to the 5-measurement space.

- **Process model**: Constant-velocity (and constant-angular-velocity)
  kinematic model. The state transition matrix `F` is:
  ```
  F = [ I₃  Δt·I₃  0    0   ]
      [ 0   I₃    0    0   ]
      [ 0   0     I₃  Δt·I₃]
      [ 0   0     0   I₃   ]
  ```
  Process noise `Q` is tuned for stylus input (small position noise,
  moderate velocity noise).

- **Latency budget**: The full Kalman update (predict + correct) must
  complete in < 2.0 ms per event. The 12×12 matrix operations use
  `nalgebra` (already a workspace dependency candidate) or a hand-rolled
  `Matrix12` with SIMD-friendly layout. The filter is `O(1)` per event
  with no allocation.

- **Pressure smoothing**: A separate 2-state Kalman filter (value + rate)
  smooths pressure data, which is typically noisier than position. The
  smoothed pressure drives line width in drawing applications.

- **Integration**: `KalmanStylus` is a standalone struct. The window
  event loop feeds raw `Tablet` events into `KalmanStylus::update`, which
  returns a `FilteredStylusState` with smoothed position, orientation,
  and pressure. Widgets consume `FilteredStylusState` instead of raw
  events.

- **Performance gate**: `KalmanStylus::update` completes in < 2.0 ms
  per event, verified by a `#[ignore]`-gated benchmark that processes
  10,000 synthetic stylus events and asserts the average per-event time
  is under the 2.0 ms budget. CI runners are the gate of record.
