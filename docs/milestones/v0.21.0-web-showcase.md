# Milestone Specification: v0.21.0 — Web Showcase & Browser Accessibility

**Status:** Implemented on `main`, pending the `v0.21.0` tag. This
document specifies the web-showcase workstream that landed after the
v0.21.0 release preparation and ships under the same pending tag
(CHANGELOG §0.21.0 covers the milestone's widget-catalog, dev-channel,
icon, and internationalization deliverables).

## 1. Executive Summary & Objectives

Milestone `v0.21.0` carries the `widget_catalog` reference application
from a desktop-only example to a dual-target (`wasm32-unknown-unknown` +
native) showcase that runs the real widget tree, layout, paint, and
accessibility pipeline in a browser tab. Three coupled deliverables make
that honest rather than demonstrational:

- **A Flutter-grade web accessibility bridge** — `martensite-access`'s
  wasm DOM/ARIA mirror is reworked into a positioned,
  bounds-accurate semantic overlay (the `flt-semantics` model) with
  editable-text projection, composite-widget relations, roving tabindex,
  and opt-in activation behind a trusted user gesture.
- **An authenticated loopback bridge for the dev channel** — a wasm app
  cannot open the ADR-0038 Unix socket, so the topology inverts: the app
  dials *out* over WebSocket to a `cargo martensite dev-web` relay that
  re-binds the ordinary dev-channel socket for local tooling, under a
  per-run bearer token, an Origin allowlist, and a read-only default
  method filter (ADR-0042).
- **CI compile coverage and static deployment** — the wasm32
  `target-checks` leg now covers the catalog and its dev-channel/gpu
  dependencies, and a dedicated `Deploy Web Catalog` workflow publishes
  the wasm build to GitHub Pages.

The governing principle is unchanged from v0.17.0 §4.3: the web target
must run the *production* pipeline — the same `CatalogView`,
`WidgetArena`, `AccessKitAdapter`, and dev-channel dispatcher — with the
honest gaps (no system fonts, no listening sockets, no `Instant::now`)
made explicit in code rather than papered over.

## 4. Architectural Deliverables & Implementation Specifications

### 4.1. Positioned Web Accessibility Bridge (`martensite-access::web`)

Landed: `0bd0452` (`crates/martensite-access/src/web.rs`,
`tests/web_mirror_dom.rs`).

There is no upstream AccessKit adapter for the web. The bridge
translates `accesskit::TreeUpdate`s into a live DOM subtree in the style
of Flutter's `flt-semantics` layer:

- **Positioned DOM mirror.** Each mirrored node owns an element
  absolutely positioned at the node's real `Node::bounds` inside the
  `data-martensite-a11y-mirror` container — pixel-accurate for
  browse-mode focus outlines and touch exploration rather than a single
  `sr-only` clip. Elements are visually transparent (`opacity: 0`,
  `pointer-events: none`) and elements without bounds collapse to a
  zero-size element at their parent's origin. Mirror state is diffed
  before writing: style, attribute, text, value, and selection writes
  are skipped when unchanged, so per-frame `DIRTY_A11Y` updates do not
  trigger DOM layout thrash.
- **Opt-in activation.** The mirror is off by default. A visually
  hidden "Enable accessibility" button is appended to the document and
  requires a *trusted* click; the programmatic paths are
  `WebA11yBridge::set_enabled` and `WebA11yBridge::builder`. While
  disabled, no per-node DOM is created — tree updates accumulate and
  apply atomically on activation. The shared live-region announcer
  exists regardless.
- **Trusted-event gate.** Every DOM event closure ignores events with
  `Event::is_trusted() == false`, so same-origin scripts cannot inject
  `ActionRequest`s through the mirror.
- **Editable-text projection.** `Role::TextInput`,
  `MultilineTextInput`, `SearchInput`, `PasswordInput`, and the rest of
  the input-role family project to real `<input>`/`<textarea>` elements
  so assistive technology receives native value, selection, and IME
  behaviour. `Role::PasswordInput` projects to
  `<input type="password">`; its value is written only into the input's
  own `value` property — never into `aria-valuetext`, text content, or
  any other DOM attribute. DOM `input`/`select` events on projected
  elements translate back into `Action::SetValue` /
  `Action::SetTextSelection` requests.
- **Composite widgets.** `Node::active_descendant`, `Node::owns`, and
  `Node::controls` mirror to `aria-activedescendant`, `aria-owns`, and
  `aria-controls` for combobox/listbox/menu/tablist patterns.
  Containers using `aria-activedescendant` keep DOM focus themselves;
  their descendants leave the tab order entirely.
- **Roving tabindex.** Composite containers (tablist, menu, menubar,
  radiogroup, toolbar, listbox, tree, grid) run roving tabindex: only
  the active item — `active_descendant`, else `selected`, else focused,
  else first focusable — carries `tabindex="0"`; all other focusable
  members carry `tabindex="-1"`. Outside composites, every focusable
  element stays in the tab order.
- **Single-channel announcer.** A separate `aria-live="polite"` element
  is the *single* announcement channel: `aria-live` is deliberately not
  mirrored onto individual elements, which would double-announce.
- **IME boundary.** `martensite_window::web::HiddenImeInput` remains a
  separate, deliberately `aria-hidden="true"` `<input>` that hosts IME
  composition and clipboard keyboard paths; it is never part of the
  mirror. `set_dom_focus_enabled(false)` prevents a mirror-side
  `focus()` from stealing DOM focus mid-composition.
- **Deliberately out of scope:** multi-`TreeId` sources (single tree,
  `TreeId::ROOT`), `html_id`/`inner_html` passthrough, and braille
  attributes. The rest of the AccessKit property surface — relations,
  position/set metadata, `aria-sort`, `aria-current`, `aria-invalid`,
  `aria-orientation`, `aria-keyshortcuts`, `lang`, `dir` — is mirrored.

### 4.2. Authenticated Loopback Dev-Channel Bridge (ADR-0042)

Landed: `98ca4e1` (`martensite-host`), `6aabe15`
(`martensite-devtools`), `a1b5ebe` (`cargo-martensite`), `f9fcc3f`
(ADR-0042).

ADR-0038 deliberately gives the dev channel no TCP listener; a wasm app
cannot open or be reached over a Unix socket, so the topology inverts —
the app dials out and acts as the dev-channel *server* over a
client-initiated WebSocket.

- **Host protocol (`martensite-host::dev_channel`).**
  `HelloParams::auth_token` is an optional bearer credential;
  `DevChannelConfig::with_auth_token` makes a session reject
  missing/mismatched tokens with `auth_failed`
  (`ERR_AUTH_FAILED = -32002`; ADR-0042 drafts this code as `-32009`,
  the shipped constant is `-32002`). No configured token ⇒ behavior is
  unchanged for existing Unix-socket clients. `MethodClass` statically
  classifies every registered RPC method `Read` or `Mutate` via
  `method_class()`; unknown methods classify `Mutate` (fail closed).
- **Wasm transport (`martensite-devtools::web_channel`).** Compiled only
  for `wasm32-unknown-unknown` under feature `web-dev-channel`:
  `WebDevChannel`/`WebChannelOptions` wrap `web_sys::WebSocket` as the
  same newline-delimited JSON-RPC line transport, `relay_url` builds
  the dial URL, and `required_token` enforces the bearer on incoming
  `hello`s. `martensite-host` is host-only, so the wasm leg exposes a
  protocol-dispatcher callback the app wires to its `DevSession`
  equivalent.
- **Relay (`cargo martensite dev-web`, feature `web-dev-channel`).**
  `serve_dev_web` binds `127.0.0.1` only — never bare `localhost`,
  which could dual-bind `::1` and widen the origin surface — on
  `ws://127.0.0.1:<port>/dev-channel` (default port `8788`,
  `DEFAULT_RELAY_PORT`). The WS upgrade requires a per-run 256-bit
  bearer `token` query parameter printed at startup, and the `Origin`
  header (when present) is checked against a loopback allowlist
  (`null`, absent, or `http(s)://{127.0.0.1,localhost,[::1]}:*`). The
  relay re-binds the ordinary per-session dev-channel Unix socket and
  is a dumb pipe after authentication, renumbering request ids to
  correlate concurrent clients. It injects the bearer into forwarded
  `hello` requests, so a wasm app requiring the token keeps end-to-end
  authentication without local tools knowing it. Only
  `MethodClass::Read` requests forward by default; `--allow-mutations`
  unlocks the table and blocked calls answer `method_blocked`
  (`ERR_METHOD_BLOCKED = -32010`; `ERR_NO_UPSTREAM = -32011` when no
  web session is attached). The tool-facing side requires a Unix domain
  socket — non-Unix builds return `RelayError::UnsupportedPlatform`.
- **Local-development only.** `ws://` on loopback is unreachable from
  HTTPS-hosted pages (mixed content / Private Network Access), so the
  bridge is never a hosted-tooling surface — by construction, matching
  the ADR-0038 posture.

### 4.3. Dual-Target Widget Catalog (`examples/widget_catalog`)

Landed: `0e2db90`.

- **Dual crate types.** `crate-type = ["cdylib", "rlib"]`: `cdylib`
  for wasm-bindgen, `rlib` so `cargo check`/`cargo test` and the native
  binary share the library.
- **Shared `App`.** `src/app.rs` drives both targets — the same
  `CatalogView`, `WidgetArena`, layout/paint pipeline, overlay sync, and
  `AccessKitAdapter`. Native-only surfaces (AccessKit platform adapter,
  dev-channel socket, headless mode, env/fs) stay cfg-gated host-only.
- **Web entry (`src/web.rs`).** `#[wasm_bindgen(start)]` binds
  `#martensite-canvas` via `martensite_web::canvas_element` +
  `prepare_canvas` (device-pixel-ratio-scaled backing store), then hands
  the shared `App` to `martensite-web`'s event-loop driver
  (`ControlFlow::Poll` + rAF). Two async legs run on the main thread:
  - *GPU probe* — `gpu::create_instance` + `gpu::gpu_context_for_web`
    perform the real `navigator.gpu` probe and log the selected
    `WebBackend`: `WebGpu` → Vello compute; `WebGl2` or no adapter →
    TinySkia CPU raster (`prefer_cpu`, enforced by the boundary in
    `martensite-wgpu::web` — Vello is compute-based and cannot run on
    WebGL2). The `wgpu::Instance` is retained for the app's lifetime
    because wgpu's wasm backend resolves surfaces/adapters through
    external handle slots.
  - *Font fetch* — the web has no system fonts, so
    `web/assets/fonts/font.ttf` (a byte-identical copy of the checked-in
    `FiraMono-Medium.ttf` fixture) is fetched and installed as the
    thread-local fixture-font source consulted by lazy `FontManager`
    creation.
- **wasm clock honesty.** `std::time::Instant::now` traps on wasm. The
  web arm reads `performance.now()` through a `now_ms` helper and
  replicates the router's pointer pipeline through its public API
  (overlay-first, capture-aware hit-test, hover enter/leave, focus
  drain, event ledger) because the router's `ClickTracker` stamps
  `Instant::now()` — the web click streak tracks on `performance.now()`
  instead. `RecoveryMachine::handle_surface_error` is likewise
  `Instant`-stamped and stays host-gated; web surface errors
  log-and-retry.
- **Real a11y wiring.** Arena `TreeUpdate`s feed `WebA11yBridge`; the
  `martensite_catalog_enable_a11y()` wasm export enables the mirror
  programmatically for tooling (the production path remains the
  bridge's hidden "Enable accessibility" button).
- **Dev channel + inspector (`src/web_dev.rs`, feature `web-dev`,
  default off).** The page URL must carry `?dev_token=<relay-token>`;
  the app then dials the `dev-web` relay and serves the real
  `DevSession` over `WebDevChannel` — hello/version/bearer handled by
  the transport, the dispatcher mirroring the host dev-channel's method
  normalization and `-32601`/`-32603` mapping. The F12 diagnostic HUD
  is `web-dev`-only. Neither leg compiles into public builds.
- **Static page.** `web/index.html` is self-contained — an inline
  module script, no third-party references; `web/pkg/` glue is
  generated per README (`cargo build --target wasm32 --release --lib`,
  `wasm-bindgen --target web`, `python3 -m http.server`).
- **Browser gate.** `tests/browser_gate.rs` is `#[ignore]`-gated behind
  `MARTENSITE_WEB_BROWSER=1` (same convention as `examples/web`): it
  builds the wasm bundle, serves `web/`, and drives headless Chromium
  to assert the start log, the GPU backend decision, the font fetch,
  the presence of `[data-martensite-a11y-mirror]`, a real projected
  role tree after programmatic enablement, and a synthetic pointer
  click with no `pageerror`. Executed locally (headless Chromium): PASS.

### 4.4. CI Coverage & GitHub Pages Deployment

Landed: `a418196`.

- **`target-checks` wasm32 leg** (`.github/workflows/ci.yml`) now
  `cargo check --target wasm32-unknown-unknown --all-targets` on
  `-p widget_catalog -p martensite-devtools -p martensite-vello` in
  addition to the existing web crates, keeping the catalog's web build
  compile-gated on every run.
- **`Deploy Web Catalog`** (`.github/workflows/deploy-catalog-pages.yml`)
  triggers on pushes to `main` touching `examples/widget_catalog/**`,
  `crates/martensite-web/**`, or `crates/martensite-*/src/web.rs`, plus
  `workflow_dispatch`. The job builds
  `cargo build -p widget_catalog --target wasm32-unknown-unknown
  --release`, generates glue with `wasm-bindgen-cli 0.2.128` (pinned
  `--locked` to the workspace lockfile's wasm-bindgen — the CLI must
  match the library or glue generation rejects the descriptor section)
  into `examples/widget_catalog/web/pkg`, then runs
  `configure-pages` → `upload-pages-artifact` → `deploy-pages` under the
  `github-pages` environment. Deployment requires GitHub Pages to be
  enabled on the repository; until then the workflow builds and stages
  the artifact without publishing.

## 7. Known Limitations & Deferred Items

- **Browser gate is environment-gated** (`MARTENSITE_WEB_BROWSER=1`,
  `#[ignore]`): it runs locally/self-hosted; PR CI compile-gates the
  wasm boundary via `target-checks` but does not drive a browser.
- **Pages deployment requires repository enablement** — the workflow
  stages artifacts on every qualifying push but only publishes once
  GitHub Pages is enabled for the repo.
- **`Instant::now()` traps on wasm** — the catalog works around it with
  `performance.now()` replicas of the click-streak and surface-error
  paths rather than a shared clock abstraction; upstreaming a wasm-safe
  clock into `martensite-window`'s router/`RecoveryMachine` is deferred.
- **`dev-web` relay is Unix-only** — the tool-facing side binds a Unix
  domain socket; non-Unix builds return `RelayError::UnsupportedPlatform`
  (a Windows named-pipe leg is deferred).
- **Web a11y scope** — single `TreeId::ROOT` tree only; no
  `html_id`/`inner_html` passthrough, no braille attributes.
- **No hosted dev tooling** — the bridge is `ws://` loopback by design;
  any `wss://`/hosted variant would be a new ADR.

## 8. Risks

- **Loopback exposure class.** A plain `ws://localhost` bridge is
  reachable from any web page in the user's browser — precisely the
  Chrome `--remote-debugging-port` failure class ADR-0038 rejects.
  Mitigated structurally: v4-loopback bind, per-run bearer, Origin
  allowlist, read-only default, feature-gated-off, and `hello`-level
  auth injection (ADR-0042).
- **Mirror/script injection.** The positioned DOM mirror could be an
  `ActionRequest` injection vector for same-origin scripts. Mitigated
  by the `is_trusted()` gate on every DOM closure, including the
  activation button.
- **Password leakage through the mirror.** `PasswordInput` values are
  written only into the projected `<input type="password">`'s `value`
  property — never into attributes or text content — so the secret
  cannot leak into the DOM-observable surface.
- **wasm-bindgen version skew.** The Pages workflow pins
  `wasm-bindgen-cli` to the lockfile version; a mismatched CLI rejects
  the descriptor section rather than silently miscompiling.
- **Docs rot.** The catalog web build is compile-gated on wasm32 in
  `target-checks`; the Pages workflow exercises the full
  build+bindgen pipeline on every push to the web surface.
